# decoding_toolbox — MVPA decoding with The Decoding Toolbox (TDT)

Two decoding pipelines built on [The Decoding Toolbox
(TDT)](https://sites.google.com/site/tdtdecodingtoolbox/), plus one helper that
decides which feature space TDT actually sees.

They answer different questions and live at different levels of the hierarchy:

| | `SVM_between_subjects` | `template_xclass_acc` |
|---|---|---|
| level | second (group) | first (within-subject), summarized at group level |
| unit of classification | one subject = one sample | one trial/condition beta = one sample |
| what is decoded | group membership (e.g. patients vs controls) | condition identity within a subject |
| cross-validation | K-fold over subjects, balanced per group | leave-one-run-out within subject |
| inference | permutation + TFCE, non-parametric throughout | sign-rank vs chance, plus repeated-measures ANOVA across conditions |
| status | **overhauled and tested** | **audited and repaired 2026-09-30, not yet re-run — see [Status](#status-and-known-issues)** |

## What this is

Unlike most domains in this repo, `decoding_toolbox/` has no `scripts/` +
`functions/` split — three files sit at the top level, two **scripts** meant to be
copied into a study's `code` subdataset and renamed, and one **function** used as
a library call.

Both scripts derive from TDT's own `decoding_template.m`, which is why they share
vocabulary (`cfg`, chunks, labels, `decoding_describe_data`, `make_design_cv`) even
though what they decode is completely different. Where they diverge, the
between-subjects script is the one that has been reworked and run in anger; the
cross-classification script is closer to the stock TDT template.

## The scripts

### `LaBGAScore_decoding_SVM_between_subjects.m`

Group-level SVM decoding of subject class (e.g. patients vs controls) with
permutation-based TFCE inference. The largest script in the repo at ~2000 lines,
and the one with the most developed header — read that header before this
section, it is authoritative.

The pipeline: build balanced K-fold CV partitions per group (optionally stratified
on further variables via `cv_strata_vars`) → configure TDT for `'searchlight'`,
`'roi'` or `'wholebrain'` → run the real decoding once → generate N permutation
designs → run permutations in parallel **in memory**, reusing `passed_data` and
`misc` from the real run so images are read and searchlight neighbourhoods
computed once rather than once per permutation → voxel-wise empirical p-values →
TFCE inference → CANlab output objects and tables.

Two points the header makes that are easy to lose and expensive to get wrong:

- **The null must be generated by the same procedure as the real statistic.** The
  permutation runs use the same classifier, the same scaling, the same
  everything. A null built differently is not the null distribution of the
  statistic you computed.
- **`scaling_regime` is a real methodological choice**, not a speed knob:
  `'kernel'` uses `classification_kernel` with `scale_estimation = 'all'` (TDT's
  own recommendation — label-blind scaling cannot carry category information
  across the train/test split, and the precomputed kernel is reused across
  permutations); `'strict'` uses `classification` with train-only `'across'`
  scaling and re-derives the linear kernel on every fold of every permutation,
  measured **12–25× slower** on a whole-brain run. `'kernel'` is the default
  because searchlight runtime is the binding constraint.

Primary inference is TFCE (Smith & Nichols 2009) via `tfce_volume`, shared with
the `secondlevel/` TFCE stack, reported as a global FWE-corrected p-value plus
voxel-wise uncorrected, FDR- and FWE-corrected TFCE maps. Voxel-wise permutation
p-values and FDR are reported alongside for interpretability, not as the primary
result.

### `LaBGAScore_decoding_template_xclass_acc.m`

Within-subject cross-classification accuracy: for each subject, classify among
the conditions named by `conds2include` using leave-one-run-out CV over the
first-level betas in that subject's `SPM.mat`, then summarize across subjects.

Per subject it writes a confusion matrix; across subjects it reports the median
and IQR confusion matrix, a per-condition accuracy distribution, a
repeated-measures ANOVA across conditions with Tukey–Kramer post-hoc
comparisons, and a Wilcoxon sign-rank test of each condition's accuracy against
chance.

Options are three lines at the top: `results_suffix`, `conds2include`,
`mask_name`. It expects `prep_s0_define_directories`, the first-level
`s1_options_dsgn_struct` (for `DSGN.modeldir`) and the second-level
`a_set_up_paths_always_run_first` (for `resultsdir`/`htmlsavedir`) to have run,
and calls each itself if the corresponding variable is missing.

It has been audited and repaired but **not re-run since** — see [Status](#status-and-known-issues).

### `LaBGAScore_export_scaled_contrasts.m`

The only function here, and the one that decides *what* gets decoded.

TDT's `cfg.files.name` points at **first-level con images**, so an SVM run
straight off the wrapper analyses raw contrasts — while the second-level GLM and
PDM analyse contrasts built from z-scored (and, where applicable,
ComBat-harmonised) condition images. The three analyses would then answer the
same question on three different feature spaces, which is not a difference anyone
wants to discover in the discussion section.

This function writes a second-level contrast object back out as ordinary
per-subject `.nii` files, so TDT consumes exactly what the GLM used, with the
provenance visible in the file list rather than injected into `passed_data`.
`'object'` selects which representation to export (`DATA_OBJ_CON` raw,
`DATA_OBJ_CONsc` z-scored conditions, `DATA_OBJ_CONscc` l2norm-scaled contrasts);
subject identity comes from `DAT.imgs`, the object's own column order, so the
mapping cannot silently desynchronise.

## Shared TDT concepts

Both scripts speak TDT's `cfg` vocabulary:

- **labels** — what is being discriminated. Between-subjects: group membership.
  Within-subject: condition identity, read from `SPM.Sess(1).U(k).name`.
- **chunks** — the cross-validation unit, held out together. Between-subjects: a
  fold of subjects. Within-subject: a run.
- **`cfg.analysis`** — `'searchlight'`, `'ROI'` or `'wholebrain'`. The
  between-subjects script supports all three; the cross-classification one is set
  to `'wholebrain'`.
- **`decoding_describe_data` → `make_design_cv` → `decoding`** — the three calls
  that turn labels, chunks and a mask into a result. Both scripts follow this
  sequence; everything else is preparation and reporting around it.
- **`cfg.results.output`** — which measure comes back. Between-subjects: AUC
  minus chance. Within-subject: `'confusion_matrix'`.

## Handling a site or nuisance confound

`SVM_between_subjects` offers **four levers**, which address different things and
can be combined. They are worth understanding as a set, because reaching for the
wrong one is easy:

| lever | what it does | what it costs |
|---|---|---|
| `subject_filter` | restricts the sample, e.g. `{'center', {'KUL'}}` — one site, no confound left | sample size |
| `cv_strata_vars` | balances the nuisance variable across CV folds | nothing, when it is achievable |
| `nuisance_resid_vars` | residualises the features on phenotype columns | **where a nuisance level contains only one class, nuisance and group are collinear and residualising removes the group signal with it** |
| `perm_within_vars` | permutes labels *within* levels when building the null, so the permuted classifier can exploit the nuisance exactly as much as the real one | fixes the **inference**; does not deflate the point estimate |

ComBat (`combat_batch_var`, `combat_ref`) is a fifth, acting on the features
rather than the design.

**The invariant across all of them is label-blindness.** Every one is applied
identically to the real and the permuted runs, and none is allowed to see the
variable being decoded. ComBat is the sharp case: telling it to preserve the
decoded variable (`mod`) would write label information into the features.
Harmonisation here is deliberately label-blind (`mod = []`), and features that
are constant across all samples, or constant within any one site, are excluded
and passed through untouched — `combat.m` errors on the first and returns `NaN`
on the second.

## Which feature space is decoded

Worth stating explicitly because it is the most common way these analyses end up
not comparable with the rest of a paper:

| route | what TDT sees |
|---|---|
| `cfg.files.name` → first-level con images | raw first-level contrasts |
| `cfg.files.name` → output of `LaBGAScore_export_scaled_contrasts` | the same images the second-level GLM and PDM used |
| within-subject `xclass_acc` | first-level **betas**, via `design_from_spm(beta_loc)` |

**A GLM path harmonised with `combat_mod = {'group'}` is not a valid feature
source for a classifier.** ComBat adds the fitted group effect back into its own
output, so every image carries a term proportional to its own subject's label —
a classifier trained on those images is reading the labels, not the brain.
`contrast_objects_tag` exists to point the export at the label-blind path in a
model that harmonises more than one way. This is the single easiest way to get a
spectacular and completely invalid decoding result out of this pipeline.

The within-subject script is a different level of analysis, so it is not expected
to match the second-level feature space — but do not compare its accuracies to a
between-subject decoding result as if they were the same measurement.

## Running and publishing

Both scripts are written to be run under MATLAB's `publish`, and both draw
figures as they go. Two practical notes:

- **`publish()` buffers a script's stdout until the script ENDS**, so a long
  decoding run shows nothing until it finishes. That is buffering, not a hang.
- **`publish()` catches a script error into the html and returns normally**, so a
  crashed run raises nothing and exits 0. Use
  [`clean/LaBGAScore_run_reports.m`](../clean/LaBGAScore_run_reports.m), which
  reads the report back and fails on `<pre class="codeoutput error">`, and prefer
  [`LaBGAScore_prov_publish`](../clean/README_provenance.md) over a bare
  `publish()` so the report carries a provenance record of every dependency
  version the run reached.

**Size `perm_chunks` to the parallel pool.** The arithmetic is identical however
the permutations are split, but the feature extraction is not: 105 chunks on a
21-worker pool means 5 waves and 5× the extraction, measured at **5.4 days**
where 21 chunks on 21 workers took well under one. Fewer chunks than workers is
the opposite error. Verify a chunked run against the per-permutation path on a
small run first.

Searchlight and permutation runs are long. Detach them (`setsid nohup … &`) rather
than relying on a terminal staying open, and see
[`LaBGAS_fMRI_analysis_workflow.md`](../LaBGAS_fMRI_analysis_workflow.md) for the
headless-vs-X2go decision.

## Dependencies

- **[The Decoding Toolbox (TDT)](https://sites.google.com/site/tdtdecodingtoolbox/)**
  on the MATLAB path — not vendored. See the
  [accompanying paper](https://www.frontiersin.org/articles/10.3389/fninf.2014.00088/full)
  and [Andy Jahn's tutorial](https://andysbrainbook.readthedocs.io/en/latest/ML/ML_Short_Course/ML_05_Haxby_MVPA.html).
- **SPM12** — both scripts read first-level `SPM.mat`/betas.
- **CanlabCore** — `fmri_mask_image`, `fmri_data`, `fmri_data_st`, `region`,
  `resample_space`.
- **LaBGAScore** with subfolders — `prep_s0_define_directories`, and for the
  between-subjects script the `secondlevel/` TFCE stack.
- **Statistics and Machine Learning Toolbox** — `fitrm`, `ranova`, `multcompare`,
  `signrank` in the cross-classification script.
- libsvm ships with TDT and is the default decoding software.

## Status and known issues

### `SVM_between_subjects` — tested

Overhauled and run in anger, including the header. Treat its header as the
authoritative description of that pipeline.

### `template_xclass_acc` — audited and repaired 2026-09-30, not yet re-run

Tested once, some time ago, and not since. An audit on 2026-09-30 found a
blocking syntax error and a set of correctness problems; all are now fixed, and
`checkcode` went from 8 messages to **0**. The script has **not been run against
data since the repairs** — that needs a study with a fitted first-level model.

**What was wrong, and what changed**

| was | now |
|---|---|
| `signrank(inputs{var},(100/size(conds2include,2));` — a missing closing parenthesis, reported by `checkcode` as `NOPAR`. **The file did not parse, so the script could not run in any form.** | fixed, and the chance level is derived rather than hardcoded (below) |
| `labelnames{label}` indexed by condition NUMBER, so `conds2include = [2 4]` populated `{2}` and `{4}` and left `{1}` and `{3}` empty — empty labels then flowed into `decoding_describe_data` and every figure | indexed by POSITION in `conds2include`, and preallocated per subject |
| the subject count was the leaked loop counter `firstsub`; right by accident, undefined if the subject list was empty | an explicit `nsubs`, with the listing filtered to directories and an error when it is empty |
| the mask was resampled to subject 1 and reused, with nothing checking the others shared that space | still resampled once, but every later subject's `dim`/`mat` is checked against the reference and a mismatch is an error |
| `signrank(…, 100/nConditions)` silently assumed TDT returns percentages; a proportion-scaled matrix would have been tested against a chance level 100× too high, returning a "significant" result for every condition | the scale is detected from the data, the chance level follows, and which one was used is printed |
| `cfg.scale.estimation = 'all'` hardcoded, with a comment claiming it is "equivalent to no scaling" | a `scaling_regime` option (`'kernel'`/`'strict'`), the same choice and the same reasoning as `SVM_between_subjects` |
| `cfg.plot_selected_voxels = 500` | `0`, as in the between-subjects script |
| `set(gcf,'WindowState','maximized')` on five figures, `drawnow, snapnow` on only one | `plugin_set_figure_size` and `drawnow, snapnow` throughout, plus a chance line on the boxplot |
| `'Colors','rgbm'` — four hardcoded colours for a variable number of conditions | `lines(n_conds)` |
| `ranovatbl`, `margmeanstbl`, `posthoctbl`, `p` and `stats` computed but never saved | saved alongside the rest |
| the `htmlsavedir` guard warned *"DSGN variable not found"*; the set-up-paths script went by three different names | both corrected |
| `['group_level_stats' cfg.analysis …]` → `group_level_statswholebrain_…` | separator added |
| three blocks of commented-out plotting code; five variables growing in loops | removed; all preallocated |

The header was rewritten to the numbered-step style used in `firstlevel/` and in
`SVM_between_subjects`: what each step does, which TDT function it calls, the
full option list including the three variables taken from the workspace rather
than set in the script, and an explicit ASSUMPTIONS block.

**What is still true of it**

- **The parametric/non-parametric mix is deliberate but unresolved.** Median and
  IQR are reported, the per-condition test against chance is a sign-rank, but
  the across-condition comparison is `fitrm`/`ranova`, which is parametric. The
  header now says so and tells you to lead with the non-parametric results if
  the accuracies are visibly non-normal. Nobody has decided whether the ANOVA
  should be replaced with a Friedman test.
- **Condition names come from `SPM.Sess(1)` only**, and all conditions are
  assumed present in all runs. Fine for the single-session designs this was
  written for; wrong for a multi-session design whose sessions differ.
- **It has not been re-run.** `checkcode` is clean and the logic has been read,
  but neither is a substitute for a real run. Run it on one subject first.
