# PLSDA_paired_neuroimaging_pipeline — User Guide

## Overview

`PLSDA_paired_neuroimaging_pipeline` is the **within-subject** member of the
PLS-DA family. It discriminates two conditions measured in the same subjects —
pre/post, on/off drug, two sessions — from raw observation rows, without letting
the pairing leak across the train/test boundary.

The other three pipelines assume independent subjects. Applying them to paired
rows would put a subject's pre and post observations on opposite sides of a
cross-validation split, so the model could recognise the subject rather than the
condition. This pipeline exists to prevent exactly that.

It returns the same `results` field names as `PLSDA_neuroimaging_pipeline`, so
`plot_PLSDA_diagnostics_neuroimaging` consumes its output unchanged.

---

# The pairing contract

```matlab
results = PLSDA_paired_neuroimaging_pipeline(X, Y, subjectID, opts)
```

| input | requirement |
|---|---|
| `X` | `[n x p]` observations × features, **one row per observation**, so `n = 2 × nSubjects` |
| `Y` | `[n x 1]` binary labels, e.g. `{'pre','post'}` or `[0 1]` |
| `subjectID` | `[n x 1]` subject identifier; each subject must appear **exactly twice**, once in each class |
| `opts` | options struct (optional) |

The pairing requirement is enforced, not assumed: the pipeline **errors** if any
subject does not contribute exactly two observations, one per class. That is
deliberate — a silently unbalanced design would quietly invalidate both the
cross-validation and the permutation scheme.

The positive class is `max(Y)`, matching the rest of the family.

---

# Cross-validation: folds over subjects, not rows

Both outer and inner folds are built over **subjects** by `makeGroupedFolds`,
then expanded to rows through `subjectID`:

```
foldID   = makeGroupedFolds(nSubjects, K)   % one fold index per SUBJECT
trainIdx = trainSubjectMask(subjIdx)        % expanded to rows
```

Both of a subject's rows therefore always land on the same side of a split.
Fold counts are capped by the number of subjects, so the pipeline degrades
gracefully on very small samples rather than producing empty folds.

Note that this is the one pipeline in the family that has **always**
re-preprocessed inside each inner fold rather than reusing the outer fold's
constants. The other three were brought into line with it during the overhaul.

---

# Permutation testing: within-subject label swaps

The null is generated by `swapWithinSubjectLabels`, which independently and with
probability 0.5 swaps the two labels **within each subject**.

This is the exchangeability-correct null for a paired design. It destroys the
condition effect while preserving the pairing, the subject means, and every
subject-level characteristic exactly. Unrestricted permutation across all rows
would break the pairing and give an invalid null.

```
results.allpermAUC
results.permAUC
results.quickCV_observed
results.permutation_p
```

`permutation_p` is computed against `results.quickCV_observed` — the observed
AUC from `quickGroupedCV`, the same estimator that generates the null — rather
than against `results.AUC`, which comes from repeated nested CV. Comparing two
different estimators across the two sides of a p-value is what produced a
measured false-positive rate near 40 % at α = 0.05 elsewhere in the family. The
convention is `(sum(perm >= obs) + 1) / (nValid + 1)`, so p is never exactly zero.

`results.AUC` remains the number to report as performance.

# Covariates

```
opts.covariates     = [n x nCov] numeric, one ROW per OBSERVATION   (default [])
opts.covariateNames = {'age','sex'}                                  (default auto)
```

Covariates are regressed out inside every fold, with coefficients estimated on
the training fold only. Because `trainIdx` is a row mask expanded from a subject
mask, the nuisance fit is automatically subject-blocked — no extra work needed.

Note the row convention: one row per **observation**, not per subject. A
subject-constant covariate is simply repeated across that subject's two rows.

## Which covariates are meaningful here

**Subject-constant covariates (age, sex, genotype) are meaningful and are not
wiped out.** This is worth stating because the intuition often runs the other
way. Scaling here uses the pooled training-fold mean rather than within-subject
centering, so between-subject nuisance variance really is present in `X` and
removing it is legitimate. Being constant within subject, such covariates are
also orthogonal to the within-subject condition contrast, so they *cannot*
remove the effect of interest.

**Covariates that vary within subject are the dangerous case.** If such a
covariate tracks the condition — a state measure recorded at both timepoints
that differs systematically pre versus post — then residualizing `X` on it
removes exactly the signal under test and drives AUC toward chance. The pipeline
warns when a covariate both varies within subject and correlates |r| > 0.3 with
the class label:

```
Warning: PLSDA_paired_neuroimaging_pipeline:covariateTracksLabel
Covariate "arousal" varies within subject and correlates r = 0.61 with the
class label. Residualizing X on it will remove signal of interest.
```

Treat that warning as a design question, not a nuisance to suppress.

`opts.residualizeY` is not offered: Y is binary.

# Options

| option | default | meaning |
|---|---|---|
| `opts.outerK` | 5 | outer folds (capped by subject count) |
| `opts.innerK` | 4 | inner folds for latent-variable tuning |
| `opts.nRepeats` | 50 | repeats of the outer CV |
| `opts.maxLV` | 4 | maximum latent variables; per-fold cap via `capLV` |
| `opts.nPerm` | 1000 | permutations |
| `opts.scale` | `'zscore'` | `'zscore'` \| `'center'` \| `'none'` |
| `opts.seed` | 1 | RNG seed; results are reproducible from it |
| `opts.covariates` | `[]` | see above |
| `opts.covariateNames` | auto | provenance only |

Unrecognised option names raise a warning rather than being silently ignored,
including near-miss capitalization such as `nrepeats` for `nRepeats`.

This pipeline has **no bootstrap stage and no learning curve**, unlike the other
three, and no global-signal baseline. `opts.nBoot`, `opts.learningSteps` and
`opts.globalFun` therefore do nothing here and will warn if supplied.

# Outputs

Same field names as `PLSDA_neuroimaging_pipeline`, so the shared plotter works
directly:

```
.AUC .ACC .SENS .SPEC
.allAUC .allACC .allSENS .allSPEC
.selectedLV .betaStore .featureWeights .meanFeatureWeight
.meanBeta .sdBeta .stabilityZ .signStability
.VIP
.finalLV .betaFinal .finalXLoadings .finalYLoadings
.varExplainedX .varExplainedY
.allpermAUC .permAUC .quickCV_observed .permutation_p
.cvObserved .cvPredicted .cvSubjectID .cvRepeatID
.covariateInfo .seed
```

`cvSubjectID` carries the original `subjectID` values rather than row indices,
which makes it straightforward to colour predicted-vs-observed plots by subject.

# Plotting

```matlab
results = PLSDA_paired_neuroimaging_pipeline(X, Y, subjectID, opts);

ROI_table = plot_PLSDA_diagnostics_neuroimaging( ...
    results, results.finalXLoadings, roiNames, atlasFile, ...
    'LV', 1, 'OutPrefix', 'PLSDA_paired_run1');
```

See `README_PLSDA_plotting.md`. As everywhere in this family, atlas integer
labels `1..p` must correspond to the column order of `X`.

# Summary

| aspect | this pipeline |
|---|---|
| design | within-subject, exactly two observations per subject |
| CV | subject-blocked grouped folds, outer and inner |
| permutation | within-subject label swap |
| covariates | fold-wise, subject-blocked automatically |
| bootstrap / learning curve | not implemented |
| plotter | `plot_PLSDA_diagnostics_neuroimaging` |
